Кейс 2. Разнородная экология,
влияние capacity

Берём 8 разных стратегий по ~12 агентов каждая (полная экология),
capacity 60%, потом перезапускаем с capacity 30%, 150 раундов
(cм. приложенный скриншот справа)

Как настроить

1. В поле "Количество агентов" ставим 100,
"Раунды" — 150, Capacity — сначала 60.
2. В блоке "Участвующие агенты" нажимаем
`+ добавить ряд` нужное число раз и собираем 8 рядов:
Random, Threshold, MovingAverage, Adaptive, Contrarian,
TrendFollower, Loyal, RegretMinimizing.
3. Количество для каждого ряда — 12 или 13, чтобы
сумма дала ровно 100. Параметры можно оставить
дефолтные.
4. Жмём "Запустить симуляцию".
5. После прогона нажимаем "Сброс", меняем
Capacity на 30, запускаем повторно.

Получаем следующую картину (cap=60)



и следующую (cap=30)



Попробуем обьяснить поведение. Разнородные стратегии гасят синхронизацию: пока Threshold-агенты решают "не идти", Contrarian идут именно потому, что в прошлый раз было пусто, MovingAverage сглаживает резкие скачки, RegretMinimizing подстраивает вероятность похода под прошлый успех. Никакая подгруппа не доминирует — посещение колеблется в узкой полосе под capacity.

Формально полезность за раунд:

benefit = attendance, если attendance ≤ capacity
benefit = −attendance, если attendance > capacity

При cap=60 экология даёт avg ≈ 38, σ ≈ 12, всего 3/150 раундов в перегрузе, efficiency ≈ 85%. При cap=30 та же толпа структурно не помещается: стратегии анкорят на отношении last/capacity, и когда capacity вдвое меньше, та же самая привычная посещаемость в 35 человек превращается в постоянный перегруз. Итог — 90/150 раундов сверх capacity и **отрицательная** суммарная полезность (−2020).



Кейс 3. Кастомный агент,
своя стратегия в песочнице

Берём 50 случайных агентов против 50 кастомных,
capacity 60%, 150 раундов (cм. приложенный скриншот справа)

Как настроить

1. "Количество агентов" — 100,
Capacity — 60, "Раунды" — 150.
2. Два ряда в блоке "Участвующие агенты":
   - тип `Random`, количество 50
   - тип `Custom`, количество 50
3. Нажимаем иконку ⚙ справа от кастомного ряда —
откроется редактор кода.
4. В редакторе нажимаем кнопку "Вставить пример" —
подложится рабочий шаблон. Заменяем его на свою
логику, например:

```js
// available: history (массив прошлых посещений), capacity (число)
function decide(history, capacity) {
  const recent = history.slice(-7);
  if (recent.length === 0) return Math.random() < 0.5;
  const avg = recent.reduce((a, b) => a + b, 0) / recent.length;

  // идём, если ожидаем недогруз с запасом 10%, иначе с вероятностью 30%
  if (avg < capacity * 0.9) return true;
  return Math.random() < 0.3;
}
```

5. Закрываем модал, жмём "Запустить симуляцию".

Получаем следующую картину



Попробуем обьяснить поведение. Кастомный код исполняется в vm2-sandbox на бэкенде — без доступа к сети, файловой системе и глобальным API. Доступны только функция `decide(history, capacity)` и `Math.random()`. Это позволяет безопасно тестировать чужие стратегии, не доверяя их коду.

Формально полезность раунда та же:

benefit = +attendance, если attendance ≤ capacity
benefit = −attendance, иначе

Логика приведённого агента: скользящее среднее за 7 раундов. Если оно явно ниже capacity (запас 10%) — идёт уверенно; на грани — идёт с вероятностью 30%. Random-агенты создают фоновый шум ~Bin(50, 0.5) ≈ 25 ± 3.5, поверх которого кастомный должен "угадать" безопасный уровень входа. Если ваш агент стабильно держит привычность ниже capacity, его строгий запас в 10% позволит ему быть в плюсе чаще, чем случайным.



Кейс 4. Динамика популяции,
расписание потоков

Моделируем "новогоднее нашествие" в небольшой зал —
резкий приток новичков в первые две недели, постепенный
отток в течение следующего месяца. Пул 200 агентов,
capacity 30, 150 раундов (cм. приложенный скриншот справа)

Как настроить

активны не все сразу).
2. Capacity — 30, "Раунды" — 150.
3. В блоке "Участвующие агенты" собираем 4 ряда
(сумма = 200):
   - Loyal — 30 (регулярные посетители)
   - Adaptive — 60
   - Random — 60 (новички, ходят на удачу)
   - Threshold — 50
4. В блоке "Динамика популяции" нажимаем "Настроить" —
откроется большое окно с настройками.

В окне ставим:

5. Включаем чекбокс "Включить динамику популяции".
6. Активная популяция:
   - Старт активных = 20 (только регулярные в начале)
   - Мин активных = 20
   - Макс активных = 200
7. Приходы:
   - Распределение = Пуассон
   - Среднее = 12
   - Расписание прихода:
     старт раунд = 1, конец раунд = 14,
     fade-in = 0, fade-out = 6
8. Уходы:
   - Распределение = Биномиальное
   - Вероятность p = 0.05
   - Расписание ухода:
     старт раунд = 20, конец раунд = 80,
     fade-in = 8, fade-out = 8
9. В правой части окна сразу появится превью-график
ожидаемых потоков — оранжевые линии (среднее ± σ
для приходов) и фиолетовые (для уходов) по раундам.
По нему видно, что приток локализован в первых двух
неделях, а отток растянут на месяц после.
10. Жмём "Сохранить", затем "Запустить симуляцию".

Попробуем обьяснить поведение. На графике три панели:
посещение, полезность и активная популяция с потоками
(оранжевые столбики — приходы, фиолетовые — уходы,
чёрная линия — текущее число активных). Активная

для distance ∈ [1, fade] (внутри fade-in или fade-out)
scheduleScale = 1 внутри окна [startRound, endRound]
scheduleScale = 0 вне расписания

Так что для приходов с mean=12, endRound=14, fadeOut=6:
раунд 14 → mean=12, раунд 15 → 12·6/7 ≈ 10.3,
раунд 16 → 12·5/7 ≈ 8.6, ..., раунд 20 → 12·1/7 ≈ 1.7,
раунд 21+ → 0. Реальный sample каждый раунд берётся
из Пуассона с этим скейленным средним.

и держат финальный baseline; Threshold/Adaptive
вначале активно идут (видят "свободно", history короткая),
учатся избегать пика только к 30-му раунду — поздно.
В жизни это серверный rush (приходы залпом, таймауты
с задержкой), Black Friday или новогодняя загрузка
любых ограниченных мощностей.
